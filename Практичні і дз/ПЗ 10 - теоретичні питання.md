### Питання 1. Що таке поліморфізм в ООП і в чому полягає його головна практична користь?
<details>
<summary>💡 Показати відповідь</summary>

**Поліморфізм** (від грец. *«багатоформність»*) — це здатність об'єктів з однаковим інтерфейсом (спільним базовим класом або інтерфейсом) мати **різну реалізацію** поведінки. Іншими словами, за принципом **«один інтерфейс — багато реалізацій»**, один і той самий рядок коду може викликати метод `pay()`, `draw()` або `calculate()`, а кожен конкретний об'єкт виконає свою власну формулу.

**Головна користь:**
- Ми пишемо універсальний код, який працює з базовим типом (`Shape[]`, `Payable[]`), не знаючи заздалегідь усіх можливих підкласів.
- Якщо в систему додається новий клас (наприклад, `Triangle` або `ApplePay`), старий код обробки масивів і методів **не потрібно переписувати** (принцип *Open/Closed*).

```java
Shape[] shapes = { new Circle(5), new Rectangle(4, 6) };
for (Shape s : shapes) {
    // Єдиний виклик s.getArea(), але для кола рахується pi*r^2, а для прямокутника a*b!
    System.out.println(s.getArea());
}
```
</details>

### Питання 2. У чому різниця між статичним (Compile-time) та динамічним (Runtime) поліморфізмом у Java?
<details>
<summary>💡 Показати відповідь</summary>

1. **Статичний поліморфізм (*Compile-time Polymorphism / Early Binding*):**
   - Реалізується через **перевантаження методів (*Method Overloading*)** — коли в одному класі є декілька методів з однаковою назвою, але **різними типами або кількістю параметрів**.
   - Який саме метод викликати, вирішує **компілятор `javac`** ще до запуску програми на основі типів аргументів.
2. **Динамічний поліморфізм (*Runtime Polymorphism / Late Binding*):**
   - Реалізується через **перевизначення методів (*Method Overriding*, `@Override`)** в ієрархії спадкування або реалізації інтерфейсу (сигнатура методу повністю збігається).
   - Який саме метод виконається, вирішує **віртуальна машина JVM під час роботи програми (Runtime)**, дивлячись на реальний тип об'єкта у пам'яті Heap.

```java
class Printer {
    // Статичний поліморфізм (Overloading):
    void print(int x) { System.out.println("Int: " + x); }
    void print(String s) { System.out.println("String: " + s); }
}
```
</details>

### Питання 3. Що таке інтерфейс (`interface`) у Java і яке логічне відношення він описує?
<details>
<summary>💡 Показати відповідь</summary>

**Інтерфейс (`interface`)** — це повністю абстрактна синтаксична конструкція в Java, яка визначає **контракт поведінки** (набір методів), який зобов'язаний реалізувати клас.

- Якщо абстрактний клас відповідає на питання **«Хто я є?» (відношення `IS-A`)**, то інтерфейс відповідає на питання **«Що я вмію робити / Яку роль виконую?» (відношення `CAN-DO`)**.
- Саме тому назви інтерфейсів у Java найчастіше закінчуються на суфікси **`-able`** або **`-ible`**: `Flyable` (здатний літати), `Comparable` (здатний до порівняння), `Serializable`, `Refundable`.
- Створити екземпляр інтерфейсу напряму через `new Flyable()` **неможливо**.

```java
public interface Flyable {
    void takeOff();
    double getMaxAltitude();
}
```
</details>

### Питання 4. За допомогою якого ключового слова клас підключає інтерфейс і скільки інтерфейсів може реалізувати один клас?
<details>
<summary>💡 Показати відповідь</summary>

Клас підключає (реалізує) інтерфейс за допомогою ключового слова **`implements`**.
На відміну від спадкування класів (`extends`), де дозволено мати **лише один** батьківський клас, один клас у Java може реалізувати **скільки завгодно інтерфейсів одночасно**, перерахувавши їх через кому!

Якщо клас одночасно успадковує базовий клас і реалізує інтерфейси, то **`extends` завжди пишеться першим**, а **`implements` — другим**:

```java
public class SmartWatch extends ElectronicDevice implements Rechargeable, WaterResistant, GpsTrackable {
    // Клас зобов'язаний реалізувати (@Override) усі абстрактні методи з усіх 3-х інтерфейсів!
}
```
</details>

### Питання 5. Які модифікатори компілятор Java автоматично (неявно) додає до полів та методів в інтерфейсі?
<details>
<summary>💡 Показати відповідь</summary>

Усередині `interface` діють суворі правила за замовчуванням:
1. **Для всіх полів (змінних):** компілятор автоматично додає **`public static final`**. Тобто в інтерфейсі не може бути звичайних полів стану об'єкта — будь-яка змінна в інтерфейсі є глобальною публічною константою!
2. **Для всіх методів без тіла:** компілятор автоматично додає **`public abstract`**.

```java
public interface MathConfig {
    double PI_APPROX = 3.14159; // Неявно: public static final double PI_APPROX = 3.14159;
    double compute(double x);   // Неявно: public abstract double compute(double x);
}
```
</details>

### Питання 6. Що таке Upcasting (висхідне приведення) і чому воно завжди безпечне?
<details>
<summary>💡 Показати відповідь</summary>

**Upcasting** — це збереження посилання на об'єкт класу-нащадка у змінній типу батьківського класу або інтерфейсу (рух «вгору» по дереву ієрархії від конкретного до загального).

Воно відбувається **неявно (автоматично)** і є абсолютно безпечним, тому що кожен об'єкт підкласу гарантовано містить усі методи, оголошені в батьківському класі або інтерфейсі:
- Кожне `Circle` *є* `Shape` (`IS-A`);
- Кожен `DeliveryDrone` *вміє* `Flyable` (`CAN-DO`).

```java
Drone d = new Drone();
Flyable f = d;        // ✅ Неявний Upcasting до інтерфейсу
AbstractDevice a = d; // ✅ Неявний Upcasting до абстрактного суперкласу
Object o = d;         // ✅ Неявний Upcasting до вершини ієрархії Object
```
</details>

### Питання 7. Для чого потрібен оператор `instanceof` і що він повертає, якщо перевірити змінну зі значенням `null`?
<details>
<summary>💡 Показати відповідь</summary>

Оператор **`об'єкт instanceof Тип`** перевіряє під час роботи програми (у Runtime), чи є реальний об'єкт у пам'яті Heap екземпляром вказаного класу, його підкласу або класу, що реалізує вказаний інтерфейс. Він повертає логічне значення `boolean` (`true` або `false`).

Його головне призначення — **безпечно перевірити тип об'єкта перед виконанням Downcasting** (приведенням до конкретного типу), щоб не отримати аварійну помилку `ClassCastException`.

**Важливе правило про `null`:**
Якщо посилання дорівнює `null`, оператор `instanceof` **НІКОЛИ не викидає `NullPointerException`**, а завжди повертає **`false`**!

```java
String text = null;
boolean check = (text instanceof String); // Поверне false (без помилки!)
```
</details>

### Питання 8. Що таке Pattern Matching для `instanceof` (починаючи з Java 16+ / Java 21) і як він спрощує код?
<details>
<summary>💡 Показати відповідь</summary>

**Pattern Matching for `instanceof`** дозволяє поєднати перевірку типу та оголошення нової приведеної змінної в **одній умові `if`**, позбавляючи від необхідності писати дужки явного касту `(TargetType) obj`:

```java
// ❌ Старий спосіб (до Java 16) — дублювання назви типу тричі:
if (device instanceof Rechargeable) {
    Rechargeable r = (Rechargeable) device;
    r.charge();
}

// ✅ Сучасний спосіб (Pattern Matching в Java 16+ / 21) — чисто і лаконічно:
if (device instanceof Rechargeable r) {
    r.charge(); // Змінна 'r' вже створена і приведена до типу Rechargeable!
}
```
Більше того, змінну `r` можна одразу використовувати в тій самій умові після оператора `&&`:
`if (device instanceof Rechargeable r && r.getBatteryPercent() < 15) { r.charge(); }`
</details>

### Питання 9. Назвіть три контексти використання ключового слова `final` у Java та що воно забороняє в кожному з них.
<details>
<summary>💡 Показати відповідь</summary>

Ключове слово **`final`** застосовується у 3-х вимірах:
1. **`final` змінна / поле / параметр (`final int MAX = 100;`):** забороняє **повторне присвоєння значення** (змінна ініціалізується рівно один раз і стає константою).
2. **`final` метод (`public final void process()`):** забороняє класам-нащадкам **перевизначати (`@Override`)** цей метод.
3. **`final` клас (`public final class String`):** повністю забороняє **спадкування від цього класу** (неможливо написати `class MyString extends String`).
</details>

### Питання 10. Чи може `final` клас реалізовувати інтерфейси (`implements`) або успадковувати абстрактний клас (`extends`)?
<details>
<summary>💡 Показати відповідь</summary>

**Так, обов'язково може!**
Слово `final` перед класом забороняє іншим класам ставати *його дітьми* (тобто робить його «листом» дерева спадкування), але **абсолютно не забороняє йому самому мати батьківський клас та реалізовувати будь-яку кількість інтерфейсів**!

```java
// Цілком легальна і дуже поширена в промисловій розробці конструкція:
public final class ImmutableInvoice extends AbstractDocument implements Printable, Auditable {
    // 1. Успадковує поля від AbstractDocument
    // 2. Реалізує контракти Printable та Auditable
    // 3. Але ніхто не може створити підклас extends ImmutableInvoice!
}
```
</details>

### Питання 11. Як працює динамічний поліморфізм у пам'яті Stack і Heap? Хто визначає доступні методи, а хто — їхню реалізацію?
<details>
<summary>💡 Показати відповідь</summary>

При виразі `Animal pet = new Dog();`:
1. **Тип посилання у Stack (`Animal` — ліворуч):** використовується **компілятором (`javac`)** на етапі компіляції. Компілятор дивиться виключно у клас `Animal`, щоб перевірити, які методи взагалі **дозволено викликати** через змінну `pet`. Якщо у `Dog` є специфічний метод `guardHouse()`, якого немає в `Animal`, виклик `pet.guardHouse()` **не скомпілюється**.
2. **Фактичний тип об'єкта у Heap (`new Dog()` — праворуч):** використовується **JVM у Runtime** через таблицю віртуальних методів (*vtable*). Коли викликається `pet.makeSound()`, JVM дивиться на реальний об'єкт у купі (`Dog`) і виконує перевизначену версію `Dog.makeSound()`.

> **Коротка формула:** *Компілятор дивиться ліворуч (на тип змінної), а JVM у Runtime дивиться праворуч (на реальний об'єкт у Heap)!*
</details>

### Питання 12. Назвіть 5 ключових архітектурних та технічних відмінностей між `abstract class` та `interface`.
<details>
<summary>💡 Показати відповідь</summary>

1. **Стан об'єкта (Поля):** Абстрактний клас може мати будь-які нестатичні поля стану (`private`, `protected` змінні для кожного об'єкта). Інтерфейс **не може зберігати стан об'єкта** — у ньому дозволені лише глобальні константи `public static final`.
2. **Конструктори:** Абстрактний клас **має конструктори** (викликаються через `super(...)` для ініціалізації полів). Інтерфейс **конструкторів не має взагалі**.
3. **Множинність:** Клас може успадкувати лише **один** абстрактний клас (`extends`), але реалізувати **багато** інтерфейсів (`implements A, B, C`).
4. **Модифікатори доступу:** В абстрактному класі методи можуть бути `protected` або package-private. В інтерфейсі всі методи контракту є `public` (допоміжні внутрішні методи з тілом можуть бути `private`).
5. **Призначення:** `abstract class` описує спільне походження та каркас сутності (**`IS-A`**), а `interface` описує здатність або роль (**`CAN-DO`**), яку можуть розділяти абсолютно неспоріднені класи.
</details>

### Питання 13. Чому наступний код НЕ скомпілюється і як його виправити?
```java
interface Movable {
    void move();
}
class Robot implements Movable {
    @Override
    void move() {
        System.out.println("Робот крокує");
    }
}
```
<details>
<summary>💡 Показати відповідь</summary>

**Причина помилки компіляції:**
В інтерфейсі `Movable` метод `void move();` неявно має модифікатор **`public abstract`**.
А у класі `Robot` перед методом `void move()` не написано жодного модифікатора, тобто він отримав доступ за замовчуванням (*package-private*).
За правилами Java при перевизначенні (`@Override`) **категорично заборонено звужувати модифікатор доступу** (з `public` до *package-private*)!

**Виправлення:** додати ключове слово `public`:
```java
class Robot implements Movable {
    @Override
    public void move() { // ✅ Обов'язково public!
        System.out.println("Робот крокує");
    }
}
```
</details>

### Питання 14. Що таке `default`-методи в інтерфейсах (Java 8+), навіщо їх додали і чи обов'язково їх перевизначати?
<details>
<summary>💡 Показати відповідь</summary>

**`default`-метод** — це метод в інтерфейсі, позначений ключовим словом `default`, який вже має **готову реалізацію (тіло `{ ... }`)**.

**Навіщо їх створили?**
1. **Зворотна сумісність (*Backward Compatibility*):** коли в стандартні інтерфейси Java (наприклад, `List` або `Collection`) потрібно було додати нові методи, без `default` усі мільйони написаних раніше класів у світі перестали б компілюватися!
2. **Зручні обчислення на базі контракту:** наприклад, якщо в інтерфейсі є абстрактний метод `getEnergyJoules()`, то метод `default double getEnergyKwh()` може автоматично ділити джоулі на $3.6 \cdot 10^6$ для всіх класів-реалізаторів.

**Чи обов'язково перевизначати?** Ні, клас успадковує `default`-метод автоматично, але за бажанням може перевизначити (`@Override`) його.
</details>

### Питання 15. Як працюють `static`-методи в інтерфейсах і чи успадковуються вони класами, що роблять `implements`?
<details>
<summary>💡 Показати відповідь</summary>

Починаючи з Java 8, в інтерфейсі можна оголошувати публічні статичні методи з тілом (`static boolean isValid(int x) { ... }`).
- Вони слугують допоміжними (утилітарними) або фабричними методами, що логічно належать цьому інтерфейсу.
- **Важливе правило:** статичні методи інтерфейсу **НЕ успадковуються** класами, що реалізують цей інтерфейс! Їх не можна викликати ні через об'єкт `myObj.isValid(5)`, ні через ім'я класу `MyClass.isValid(5)` — **виключно через точне ім'я самого інтерфейсу**:

```java
public interface Validator {
    static boolean isPositive(int x) { return x > 0; }
}
// Виклик:
boolean ok = Validator.isPositive(10); // ✅ Тільки через ім'я інтерфейсу!
```
</details>

### Питання 16. Якщо поле масиву оголошене як `private final int[] numbers = {1, 2, 3};`, чи можна змінити `numbers[0] = 99;`? Чому?
<details>
<summary>💡 Показати відповідь</summary>

**Так, `numbers[0] = 99;` виконається без жодної помилки!**

**Чому?**
Тому що ключове слово `final` перед посилальною змінною (масивом чи об'єктом) робить константою **лише саме посилання (адресу в Stack)**, а не сам об'єкт у купі (Heap)!
- Написати `numbers = new int[]{4, 5, 6};` — **заборонено** (компілятор не дозволить переприв'язати посилання на інший масив).
- Написати `numbers[0] = 99;` — **дозволено**, бо ми змінюємо комірку всередині того самого масиву в Heap.
Саме тому для справжньої незмінності (*Immutability*) одного лише слова `final` біля масиву недостатньо — обов'язково потрібне ще й **захисне копіювання (`Arrays.copyOf`)**!
</details>

### Питання 17. Що таке «Порожнє фінальне поле» (*Blank final field*) і де саме воно зобов'язане отримати значення?
<details>
<summary>💡 Показати відповідь</summary>

**Blank final field** — це `final` поле екземпляра класу (`private final String id;`), якому **не присвоїли значення одразу в рядку оголошення**.

**Правило компілятора:**
Порожнє `final` поле екземпляра **обов'язково має бути ініціалізоване до завершення роботи КОЖНОГО конструктора класу** (або в блоці ініціалізації екземпляра `{ ... }`). Якщо у класі є 3 перевантажені конструктори, і хоча б в одному з них ви забули присвоїти значення цьому полю, код не скомпілюється (*Variable 'id' might not have been initialized*)!

```java
public class Passport {
    private final String serialNumber; // Blank final field

    public Passport(String serialNumber) {
        this.serialNumber = serialNumber; // ✅ Ініціалізовано рівно 1 раз у конструкторі!
    }
}
```
</details>

### Питання 18. Чому шаблонні методи (*Template Method*) у базових абстрактних класах майже завжди оголошують із модифікатором `final`?
<details>
<summary>💡 Показати відповідь</summary>

У патерні **Шаблонний метод (*Template Method*)** метод базового абстрактного класу задає **фіксований, незмінний скелет алгоритму** (наприклад: `1. перевірити авторизацію` $\to$ `2. обчислити комісію` $\to$ `3. виконати переказ` $\to$ `4. записати аудит-лог`), викликаючи всередині абстрактні методи нащадків.

Якщо не позначити цей головний метод словом **`final`**, то автор підкласу зможе перевизначити (`@Override`) весь шаблонний метод і випадково або навмисно викинути з нього крок перевірки авторизації чи логування! Модифікатор `public final` гарантує, що нащадки можуть налаштовувати лише дозволені абстрактні кроки, але не можуть зламати послідовність самого алгоритму.
</details>

### Питання 19. Чому комбінація модифікаторів `abstract final` (для класу або методу) викликає помилку компіляції?
<details>
<summary>💡 Показати відповідь</summary>

Модифікатори `abstract` та `final` мають **прямо протилежний зміст**:
- **`abstract`** означає: *«Цей клас є незавершеним шаблоном, від нього ОБОВ'ЯЗКОВО потрібно успадкуватися (`extends`), а цей метод ОБОВ'ЯЗКОВО потрібно перевизначити (`@Override`) у нащадку»*.
- **`final`** означає: *«Від цього класу КАТЕГОРИЧНО ЗАБОРОНЕНО успадковуватися, а цей метод КАТЕГОРИЧНО ЗАБОРОНЕНО перевизначати»*.

Якби існував `abstract final class`, ви б не змогли ні створити його об'єкт через `new` (бо він `abstract`), ні створити його підклас через `extends` (бо він `final`). Тому компілятор одразу блокує таку комбінацію: `Illegal combination of modifiers: 'abstract' and 'final'`.
</details>

### Питання 20. Яке ключове слово використовується, коли один інтерфейс розширює інший інтерфейс (або декілька інтерфейсів)?
<details>
<summary>💡 Показати відповідь</summary>

Між двома інтерфейсами використовується ключове слово **`extends`** (а НЕ `implements`!), причому один інтерфейс може розширювати **одразу декілька батьківських інтерфейсів** через кому:

```java
interface Readable { void read(); }
interface Writable { void write(); }

// Інтерфейс розширює ДВА інших інтерфейси через extends!
public interface ReadWriteChannel extends Readable, Writable {
    void flush();
}
```
А от клас, який реалізує `ReadWriteChannel`, використовуватиме слово `implements` і буде зобов'язаний реалізувати всі 3 методи (`read()`, `write()`, `flush()`).
</details>

### Питання 21. Що виведе цей код і чому? (Поліморфізм методів проти полів класу!)
```java
class Base {
    String label = "BaseField";
    String getLabel() { return "BaseMethod"; }
}
class Derived extends Base {
    String label = "DerivedField";
    @Override
    String getLabel() { return "DerivedMethod"; }
}
public class Test {
    public static void main(String[] args) {
        Base ref = new Derived();
        System.out.println(ref.label + " | " + ref.getLabel());
    }
}
```
<details>
<summary>💡 Показати відповідь</summary>

**Результат у консолі:**
```text
BaseField | DerivedMethod
```

**Чому так відбувається? (Класичне питання на співбесіді!):**
- У Java **динамічний поліморфізм (пізнє зв'язування) працює ТІЛЬКИ для нестатичних методів екземпляра**! Тому виклик `ref.getLabel()` дивиться на реальний об'єкт у Heap (`new Derived()`) і повертає `"DerivedMethod"`.
- А **поля класів (і `static`-методи) НЕ є поліморфними**! Оголошення поля `String label` у підкласі не перевизначає батьківське поле, а лише *приховує (hides / shadows)* його. Доступ до полів (`ref.label`) вирішується компілятором статично за **типом посилання ліворуч (`Base`)**, тому береться `"BaseField"`!
</details>

### Питання 22. Як у Java вирішується «Проблема Ромба» (*Diamond Problem*), якщо клас реалізує два інтерфейси з однаковим `default`-методом?
<details>
<summary>💡 Показати відповідь</summary>

Якщо інтерфейс `A` має `default void log()`, і інтерфейс `B` також має `default void log()`, а клас `Service implements A, B` не перевизначить цей метод — виникне **помилка компіляції**:
`class Service inherits unrelated defaults for log() from types A and B`.

**Як вирішити?**
1. Клас `Service` **зобов'язаний явно перевизначити** `@Override public void log()`.
2. Якщо всередині цього методу потрібно викликати реалізацію з конкретного інтерфейсу `A` або `B`, використовується спеціальний синтаксис **`Ім'яІнтерфейсу.super.назваМетоду()`**:

```java
public class Service implements A, B {
    @Override
    public void log() {
        A.super.log(); // Виклик default-методу з інтерфейсу A
        B.super.log(); // Виклик default-методу з інтерфейсу B
    }
}
```
**Бонус-правило (Клас завжди перемагає інтерфейс):** якщо метод `public void log()` також є у батьківському *класі* (`class Base`), і ми пишемо `class Service extends Base implements A`, то конфлікту не буде — автоматично переможе реалізація з батьківського класу `Base`!
</details>

### Питання 23. Що станеться у цьому коді: помилка компіляції чи помилка під час виконання (Runtime)?
```java
interface Flyable { void fly(); }
class Dog { }
final class Bulldog extends Dog { }

public class CastPuzzle {
    public static void main(String[] args) {
        Dog d = new Dog();
        Bulldog b = new Bulldog();

        boolean test1 = (d instanceof Flyable); // Рядок А
        boolean test2 = (b instanceof Flyable); // Рядок Б
    }
}
```
<details>
<summary>💡 Показати відповідь</summary>

**Це улюблене питання інтерв'юерів на глибоке розуміння `instanceof` та `final` класів!**
- **Рядок А (`d instanceof Flyable`) — УСПІШНО СКОМПІЛЮЄТЬСЯ** і у Runtime поверне `false`!
  *Чому компілятор це дозволяє?* Хоча сам клас `Dog` не реалізує `Flyable`, клас `Dog` **не є `final`**. Отже, теоретично десь у програмі може існувати підклас `class CyberDog extends Dog implements Flyable`, і змінна `d` могла б посилатися на нього!
- **Рядок Б (`b instanceof Flyable`) — ПОМИЛКА КОМПІЛЯЦІЇ (`Inconvertible types`)!**
  *Чому компілятор блокує цей рядок?* Тому що клас `Bulldog` оголошений як **`final`**! Компілятор на 100% знає: сам `Bulldog` не реалізує `Flyable`, і **жодного класу-нащадка у `Bulldog` бути не може**! Отже, об'єкт у змінній `b` ні за яких обставин не може бути `Flyable`.
</details>

### Питання 24. Чи можна у підкласі перевизначити (`@Override`) метод з модифікатором `private` або `static`? Що станеться, якщо оголосити в підкласі метод із такою ж сигнатурою?
<details>
<summary>💡 Показати відповідь</summary>

**Ні, перевизначити (`@Override`) не можна ні `private`, ні `static` метод!**
1. **`private` метод** взагалі невидимий за межами батьківського класу (він неявно є `final`). Якщо у підкласі створити метод з такою самою назвою — це буде абсолютно новий, незалежний метод підкласу (якщо поставити над ним `@Override`, компілятор видасть помилку).
2. **`static` метод** належить самому класу, а не об'єкту. Якщо оголосити у підкласі такий самий `static` метод, відбудеться не перевизначення (*Overriding*), а **приховування методу (*Method Hiding*)**: при виклику через змінну базового типу `Base b = new Sub(); b.staticMethod();` виконається метод класу `Base`!
</details>

### Питання 25. У чому полягає небезпека виклику абстрактного (або поліморфного) методу всередині конструктора базового класу?
<details>
<summary>💡 Показати відповідь</summary>

Погляньте на цей небезпечний код:
```java
abstract class BaseSensor {
    BaseSensor() {
        printStatus(); // ⚠️ НЕБЕЗПЕКА! Поліморфний виклик із конструктора!
    }
    abstract void printStatus();
}

class ThermalSensor extends BaseSensor {
    private String unit = "Celsius";

    @Override
    void printStatus() {
        System.out.println("Одиниця: " + unit.toUpperCase());
    }
}
```
**Що станеться при `new ThermalSensor()`?** Вилетить **`NullPointerException`**!
**Чому?** Коли створюється `ThermalSensor`, спочатку виконується конструктор батька `BaseSensor()`. У цей момент поле нащадка `unit = "Celsius"` **ще НЕ ініціалізоване** (воно дорівнює `null`)! Але через динамічне зв'язування конструктор батька викликає перевизначений метод `ThermalSensor.printStatus()`, який звертається до `unit.toUpperCase()`, коли `unit == null`!

> **Золоте правило:** Ніколи не викликайте з конструктора методи, які можуть бути перевизначені у нащадках (викликайте з конструктора лише `private` або `final` методи!).
</details>

### Питання 26. Що таке «Коваріантний тип повернення» (*Covariant Return Type*) при перевизначенні методів у поліморфізмі?
<details>
<summary>💡 Показати відповідь</summary>

Починаючи з Java 5, при перевизначенні методу (`@Override`) у класі-нащадку дозволено змінити тип значення, що повертається, на **більш вузький (спеціалізований) підклас** того типу, який вказано у батьківському методі або інтерфейсі!

```java
abstract class ShapeFactory {
    public abstract Shape create(); // Повертає базовий тип Shape
}

class CircleFactory extends ShapeFactory {
    @Override
    public Circle create() { // ✅ Коваріантний тип повернення (Circle extends Shape)!
        return new Circle(10.0);
    }
}
```
Це дуже зручно, бо при роботі напряму з `CircleFactory` нам не потрібно робити зайвий каст `(Circle)` після виклику `create()`. *(Для примітивних типів, наприклад `int` та `double`, це не працює — лише для об'єктних ієрархій).*
</details>

### Питання 27. Коли використання `instanceof` є архітектурним антипатерном (порушенням ООП), а коли воно є виправданим?
<details>
<summary>💡 Показати відповідь</summary>

1. **❌ Коли `instanceof` — це АНТИПАТЕРН:**
   Коли замість поліморфного методу в базовому класі/інтерфейсі програміст пише каскад `if-else`:
   ```java
   // ❌ ПОГАНИЙ КОД (Порушення принципу Open/Closed):
   if (emp instanceof Developer d) total += d.calcDevSalary();
   else if (emp instanceof Manager m) total += m.calcMgrSalary();
   ```
   Якщо додати нову посаду `Tester`, доведеться шукати й переписувати всі такі `if-else` у проєкті! Правильне рішення — єдиний поліморфний метод `emp.calculateSalary()`.

2. **✅ Коли `instanceof` — ВИПРАВДАНИЙ і необхідний:**
   Коли ми обходимо гетерогенну колекцію базових об'єктів і хочемо перевірити наявність **опціональної, додаткової ролі (інтерфейсу)**, яка властива лише частині об'єктів (наприклад, серед усіх пристроїв `Device[]` зарядити лише ті, що `instanceof Rechargeable`, або при реалізації методу `equals(Object obj)`).
</details>

### Питання 28. Чи може абстрактний клас реалізувати інтерфейс (`implements`), не реалізуючи жодного його методу?
<details>
<summary>💡 Показати відповідь</summary>

**Так, може!**
Звичайний (конкретний) клас при `implements SomeInterface` зобов'язаний надати тіло для всіх абстрактних методів інтерфейсу.
Але **абстрактний клас (`abstract class`) має право НЕ реалізовувати частину або навіть усі методи інтерфейсу**, просто перекладаючи цей обов'язок далі на свої перші конкретні класи-нащадки!

```java
interface Payable {
    double calculatePay();
    String getCurrency();
}

// Абстрактний клас реалізував лише один метод з двох — і це цілком законно!
abstract class AbstractContractor implements Payable {
    @Override
    public String getCurrency() { return "UAH"; }
    // А метод calculatePay() залишається абстрактним для майбутніх підкласів!
}
```
</details>

### Питання 29. Навіщо в сучасній Java (починаючи з Java 9) дозволили створювати `private` методи всередині інтерфейсів?
<details>
<summary>💡 Показати відповідь</summary>

У Java 8 в інтерфейсах з'явилися `default` та `static` методи з тілом. Якщо в одному інтерфейсі є три різні `default`-методи, які використовують однаковий допоміжний шматок коду (наприклад, форматування заголовка чи перевірку підключення), виникла проблема дублювання коду (порушення *DRY*).
Винести цей спільний код в окремий `default`-метод було погано, бо тоді він ставав би `public` і засмічував публічний контракт інтерфейсу для зовнішнього світу.

Тому в **Java 9** дозволили створювати **`private` та `private static` методи всередині інтерфейсу**:
- Вони **мають тіло `{ ... }`**;
- Вони **не видимі** для класів-нащадків і зовнішнього коду;
- Їхня єдина мета — прибрати дублювання коду між `default` та `static` методами всередині самого інтерфейсу!
</details>

### Питання 30. Чому в стандартній бібліотеці Java клас `String` оголошений як `public final class String`, і що було б, якби він не був `final`?
<details>
<summary>💡 Показати відповідь</summary>

Клас `String` є `final`, щоб гарантувати **абсолютну незмінність (*Immutability*)** кожного рядка в Java. Якби `String` не був `final`, будь-хто міг би створити підклас `class MutableEvilString extends String`, перевизначити методи й змінювати вміст рядка «на льоту» після передачі його в чужий метод.

Це призвело б до трьох катастроф:
1. **Діра в безпеці (*Security Breach*):** рядки передають імена файлів, URL-адреси, паролі та мережеві хости. Після перевірки безпеки зловмисний підклас міг би підмінити шлях `"/safe/file.txt"` на `"/etc/passwd"`.
2. **Руйнування `String Pool` (Кешування рядків):** JVM зберігає однакові рядкові літерали в одній області пам'яті для економії гігабайтів RAM. Якби один змінив рядок, він би зламався в усіх інших частинах програми.
3. **Поломка хеш-таблиць та багатопоточності:** `String` безпечно читається з різних потоків без синхронізації і кешує свій `hashCode()`.

Водночас, попри те що `String` є `final`, він реалізує інтерфейси `Serializable`, `Comparable<String>`, `CharSequence` і чудово працює поліморфно через `CharSequence`!
</details>
